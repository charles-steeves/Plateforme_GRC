# DATA_MODEL — CONTRAT SQL ET MÉTIER v3.0
SQLite via PDO, SQL standard compatible autant que raisonnable avec une migration future vers MySQL. Tous les montants sont des **INTEGER XAF** non négatifs. L'heure est enregistrée en UTC, ISO 8601 terminé par Z. Activer PRAGMA foreign_keys=ON **sur chaque connexion**. Transactions avec BEGIN IMMEDIATE pour réservation/écriture de commandes, pas de stock négatif. Aucune donnée véritable.
## Tables et colonnes
- users(id INTEGER PRIMARY KEY, name TEXT NOT NULL, email TEXT NOT NULL UNIQUE COLLATE NOCASE, password_hash TEXT NOT NULL, role TEXT NOT NULL DEFAULT 'client' CHECK role IN ('client','admin'), created_at TEXT NOT NULL). Jamais de champ role accepté pendant l'inscription publique.
- products(id INTEGER PRIMARY KEY, name TEXT NOT NULL, description TEXT NOT NULL DEFAULT '', category TEXT NOT NULL, price_xaf INTEGER NOT NULL CHECK(price_xaf>=0), stock_quantity INTEGER NOT NULL CHECK(stock_quantity>=0), image_url TEXT NOT NULL DEFAULT '', active INTEGER NOT NULL DEFAULT 1 CHECK(active IN (0,1)), created_at TEXT NOT NULL, updated_at TEXT NOT NULL).
- orders(id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users(id), status TEXT NOT NULL DEFAULT 'pending' CHECK(status IN ('pending','confirmed','delivered','cancelled')), total_xaf INTEGER NOT NULL CHECK(total_xaf>=0), created_at TEXT NOT NULL, updated_at TEXT NOT NULL).
- order_items(id INTEGER PRIMARY KEY, order_id INTEGER NOT NULL REFERENCES orders(id), product_id INTEGER NOT NULL REFERENCES products(id), product_name TEXT NOT NULL, quantity INTEGER NOT NULL CHECK(quantity>0), unit_price_xaf INTEGER NOT NULL CHECK(unit_price_xaf>=0), line_total_xaf INTEGER NOT NULL CHECK(line_total_xaf>=0)).
- tickets(id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users(id), order_id INTEGER REFERENCES orders(id), subject TEXT NOT NULL, description TEXT NOT NULL, category TEXT NOT NULL DEFAULT 'sav', status TEXT NOT NULL DEFAULT 'open' CHECK(status IN ('open','in_progress','resolved','closed')), created_at TEXT NOT NULL, updated_at TEXT NOT NULL).
- ticket_messages(id INTEGER PRIMARY KEY, ticket_id INTEGER NOT NULL REFERENCES tickets(id), author_user_id INTEGER NOT NULL REFERENCES users(id), body TEXT NOT NULL, created_at TEXT NOT NULL).
- feedback(id INTEGER PRIMARY KEY, order_id INTEGER NOT NULL UNIQUE REFERENCES orders(id), user_id INTEGER NOT NULL REFERENCES users(id), rating INTEGER NOT NULL CHECK(rating BETWEEN 1 AND 5), comment TEXT NOT NULL DEFAULT '', created_at TEXT NOT NULL).
- loyalty_transactions(id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users(id), order_id INTEGER REFERENCES orders(id), points_delta INTEGER NOT NULL, reason TEXT NOT NULL, created_at TEXT NOT NULL, UNIQUE(order_id,reason)).
- login_attempts(id INTEGER PRIMARY KEY, subject_hash TEXT NOT NULL, attempted_at TEXT NOT NULL). Stocker un identifiant pseudonymisé/empreinte non réversible du couple identifiant+adresse IP, aucune IP ou mot de passe en clair ; purger les entrées anciennes. Variante fichier/rate-limiter possible seulement sur validation du coordinateur.

## Règles métier
Commande : le serveur accepte une liste de {product_id,quantity}, rejette doublons d'ID plutôt que de compter sur le client pour les fusionner, refuse quantité <=0, bornes configurables (1..20 unité par ligne, <=30 lignes) ; ne lit jamais un prix fourni par le navigateur. Dans transaction BEGIN IMMEDIATE : lire produits actifs, vérifier stock, décrémenter une seule fois à création, insérer orders et order_items, calculer total avec entiers et contrôle débordement ; commit ou rollback complet. Statut initial pending.
Transitions commande : pending -> confirmed / cancelled ; confirmed -> delivered / cancelled ; delivered et cancelled terminaux. PATCH avec même statut = opération idempotente sans effet supplémentaire, sauf si le statut antérieur réel est différent de la transition demandée. Lors de cancelled, restaurer les stocks une fois pour les commandes auparavant pending ou confirmed ; ne jamais restaurer pour une commande déjà cancelled. Les quantités produit n'évoluent pas lors de la livraison.
Fidélité : à la **première transition vers delivered**, attribuer floor(total_xaf / 1000) points, transaction loyalty_transactions avec reason='delivery_credit' unique par order_id, au sein de la même transaction SQL. Solde = SUM(points_delta). Aucun solde modifiable directement par le navigateur. Aucune dépense de points en P0.
Ticket : ordre lié facultatif ; si renseigné, appartient obligatoirement au client demandeur. Auteur d'un message = session réelle, pas ID client transmis. Client ne voit que ses tickets ; admin tous. Transitions ticket open -> in_progress / resolved / closed ; in_progress -> resolved / closed ; resolved -> closed / in_progress ; closed terminal. Messages permis sur open, in_progress, resolved ; sur closed, renvoyer 409.
Satisfaction : un seul avis par commande réellement delivered, appartenant au demandeur ; note 1..5, commentaire facultatif, pas d'édition en P0.
Segmentation sur commandes **non annulées** : inactive si dernier achat >90 jours UTC ; sinon regular si >=3 commandes, occasional si 2, new si 1 ; no_purchase sinon. L'ordre de priorité est inactive puis nombre ; utilisateurs admin exclus. no_purchase n'est pas automatiquement prospect commercial.
Dashboard admin : count clients (users role=client), count orders non annulées, ca_simule_xaf = SUM(total_xaf sur delivered seulement), tickets_open_count = count open/in_progress, satisfaction_avg = AVG(feedback.rating) ou null, customers_inactive_count calculé, order_status_counts. Toujours présenter « données fictives ».
## Initialisation et seed
database/init.php : CLI compatible Windows/Linux, création schema, seed reproductible depuis une base absente ; n'écrase jamais silencieusement une base existante (option explicite --reset seulement local). Minimum 12 produits, 8 clients fictifs + 1 admin ; commandes variées, tickets et points cohérents. Ne pas committer storage/*.sqlite ; documentation d'identifiants de démo localement uniquement, sans réutiliser secrets en vrai.
## Données sensibles
Mots de passe exclusivement hachés avec password_hash (PASSWORD_DEFAULT) ; seed via PHP CLI, pas de hash inventé et pas de mots de passe clairs en SQL. Traitements du contrôleur imposent les FK et vérifications de propriétaire. Schéma présent sur Git = code de création, **pas fichier de données actives**.
